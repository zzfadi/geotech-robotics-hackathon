# Two people at one robot table: performance capture and simulated contact

**Demo:** One Quest 3 wearer and a different webcam performer share a physical table. Treat each as a remote participant: the simulation consumes their published poses, never local headset state or Unreal editor transactions. Both people can make contact with the *simulated* robot. A headset overlay of the simulated arm on the real arm is a second milestone.

## What works on the development Mac

- UE **5.8.3 CL 58210709** includes a native arm64/x86_64 Live Link Hub. The shipped app at `Engine/Binaries/Mac/LiveLinkHub.app` launched, initialized the Hub module, started its UDP bridge and completed engine initialization alongside the one existing TheHumanTouch editor. No second project editor was launched. The standalone [Epic Store listing](https://store.epicgames.com/en-US/p/livelink-hub-2ed588) lists Windows; [Epic's 5.8 release documentation](https://dev.epicgames.com/documentation/unreal-engine/metahuman-known-issues-5-8-in-unreal-engine) also documents Hub on macOS. No Windows relay is needed for this installation.
- The [project](../Unreal/TheHumanTouch/TheHumanTouch.uproject) enables LiveLink and OpenXR. The project enables the built-in LiveLinkHub plugin for editor targets. Editors opened before this setting changed need a coordinated restart after saving their work. In Hub, confirm the intended editor in **Clients** and the two distinct Animation subjects in UE's **Live Link** panel. The [join launcher](../Unreal/TheHumanTouch/Tools/join_human_touch.py) binds UDP Messaging to the VPN interface; check compatible interface/static endpoints if discovery fails. Preserve the existing Concert endpoint. A connected editor or green subject alone does not prove a correctly animated body. [Epic quick start](https://dev.epicgames.com/documentation/unreal-engine/live-link-hub-quick-start-in-unreal-engine).
- On this Mac, outside UE, MediaPipe 1.2.2 Pose Landmarker Lite on CPU returned 33 image and 33 hip-relative 3D landmarks in 110/110 iterations over [Google's test image](https://storage.googleapis.com/mediapipe-assets/pose.jpg). After 10 warmups, median 8.1 ms and p95 11.4 ms for the synchronous detector call; VIDEO mode, same 1000 × 667 image, 33 ms input timestamp increments. This measures warm inference on one repeated pose, **not** webcam FPS, reacquisition, hand tracking, or motion-to-display latency.
- Subsequent implementation verified a live Quest subject in the editor, the webcam source on a reference image, and a two-person synthetic contact rehearsal. Live webcam acquisition, shared physical registration, real reaches and the headset overlay remain open. The [current scene](maker-arm-model.md) contains the official Maker Arm visual geometry, with collision and camera calibration still outstanding. See the [capture instructions](../Capture/README.md) for current implementation and verification.

## Put the split before Unreal

```text
Quest 3: wearer A, upper body + hands ─┐
                                       ├─► Mac pose service: ID, capture time, calibration, validity
RGB webcam: performer B, pose + hands ─┘        ├─► external simulator: time-aligned kinematic human colliders
                                                └─► skeletal Live Link source → local Hub → Unreal avatars
external simulator ─► robot joints, object poses, contact events + input frame IDs → Unreal & Quest
real arm telemetry ─► measured joint state (read-only reference for registration/overlay)
```

Use two independent subjects, e.g. `Human_Quest_A` and `Human_Cam_B`. Hub can route and record them together; never merge two people's skeletons into one virtual subject. Prefer Hub on this Mac for takes and multiple editors. Use the same skeletal source in the editor directly if Hub adds too much delay or the plugin cannot load in Hub. Remote Windows is an optional additional viewer/recorder; put it in the critical path only if a necessary source is Windows-only and the measured budget allows it. Live Link transports animation; it does not estimate the pose, resolve depth, synchronize a robot controller or calculate collisions.

**Quest A.** Use one foreground standalone Quest application. Sample Meta Movement/OpenXR's default upper-body skeleton: 18 core and 52 hand joints, including finger articulation. Locate the headset/view pose in the same tracking space/time for an explicit head reference. Track hands optically with controllers put down; publish position/orientation validity, body confidence, skeleton version and recenter events. Distinguish an inferred elbow from a measured headset; keep per-joint flags where the API exposes them. Map the runtime's time to the station clock and identify predicted poses as predicted. For the overlay milestone, add sending and rendering to that *same app*. A separate capture APK and an immersive viewer cannot both own the foreground XR session. Use a compatible Meta XR package in the Quest target; avoid switching the shared desktop editor's XR backend to make standalone tracking work. [Native API](https://developers.meta.com/vr/documentation/native/android/move-body-tracking/) · [Meta's Unreal Movement/Live Link sample](https://developers.meta.com/vr/documentation/unreal/unreal-movement-overview/) · [UE version compatibility](https://developers.meta.com/vr/documentation/unreal/unreal-compatibility-matrix/).

**Webcam B.** Place one fixed, oblique person-facing camera far enough back to see shoulders, arms and hips; frame the feet if legs are wanted. The overhead robot camera is a policy view and might see only hands. Use MediaPipe Pose Landmarker outside Unreal; add Hand Landmarker (two hands) to the **same timestamped image** where finger articulation is needed. Pose outputs 33 points, not joint rotations; the hand model outputs 21 per visible hand in a separate hand-centered frame. Fit fixed-length segments and parent-relative rotations using a neutral pose and sleeve/torso directions, anchor hands at the matching wrists, and leave unobservable twist and obscured legs inferred/invalid. Retain image coordinates and per-joint visibility. Assign the webcam performer to a marked starting area or ROI; if both people enter view, maintain identity by continuity and exclude the Quest wearer. On an ambiguous re-entry, invalidate B and reacquire instead of swapping their identities. [Pose outputs](https://ai.google.dev/edge/mediapipe/solutions/vision/pose_landmarker/python) · [hand outputs](https://ai.google.dev/edge/mediapipe/solutions/vision/hand_landmarker/python).

**Position in the room.** A calibrated webcam lens and table marker locate the *camera*, not a hip-relative body. Estimate B's root translation/scale from image rays plus body-scale calibration; for the first contact demo constrain the reach to a calibrated tabletop region and test touches on known points at more than one height. A plane homography alone cannot recover an elevated hand. If held-out 3D error exceeds the contact tolerance, constrain B's contacts to the demonstrated plane/volume and keep the rest visual. A second calibrated view or depth camera is the upgrade for unrestricted 3D contact. Avoid using invented depth to generate a collision.

**Adapter into Unreal.** The project now includes a Mac-compatible receiver (`ILiveLinkSource` and factory) for the pose-service wire format. Build it for this UE release, declare `SupportedPrograms: ["LiveLinkHub"]` as in the installed Hub descriptor, and register its plugin directory in Hub; loading in the editor and in Hub are separate checks. An ordinary UDP/JSON packet is not a Live Link Message Bus message. Alternatively publish via an engine-linked `ILiveLinkProvider` to the stock Message Bus source. Emit `FLiveLinkSkeletonStaticData` with bone names/parent indices once and after hierarchy changes, and `FLiveLinkAnimationFrameData` with one parent-local transform per bone each frame. Use an Animation Blueprint Live Link Pose node with a matching hierarchy or retarget asset. Validate a known left/right asymmetric pose and independent finger curls. Room translation belongs on the root once; test handedness, units and neutral rotations before retargeting to an avatar. No per-frame Concert edits. [Source development](https://dev.epicgames.com/documentation/unreal-engine/live-link-plugin-development-in-unreal-engine) · [Hub plugins and routing](https://dev.epicgames.com/documentation/unreal-engine/live-link-hub-ui-reference-for-unreal-engine).

## Time and contact: one simulated answer

Use a station-local monotonic timeline. Each source frame carries session/actor/source IDs, sequence number, original sample time and clock domain, mapped station time and uncertainty, calibration and skeleton revisions, and joint poses/validity. Use acquisition timestamps, or label host-dequeue time as an approximation; do not stamp on inference completion. Periodically measure Quest-to-host clock offset and drift with round-trip exchanges; reject high-RTT samples. Store headset prediction horizon separately. A shared wall-clock label or Hub timecode alone does not align two monotonic clocks.

Start with a 60 Hz external simulation and interpolate each actor to the same target time from a short buffer sized from *measured* jitter. Keep native capture rates. Use tick ID, the actual (possibly bracketing) input sequences/weights, applied sample time, and contact IDs on simulator output. Display the matching sampled human pose and robot/object states in Unreal; if strict visual agreement is required, publish the simulator's selected/resampled poses as the authoritative display subjects instead of each viewport choosing its own “latest.” Detect stale, out-of-order and missing joints. Suspend that collision proxy on loss; re-arm only after stable reacquisition, never sweep it across the room on a jump. Archive the inputs and outputs so the same interaction can be replayed as if remote.

The robot team is exploring Dream Labs’ zero-shot Dream-1 policy for MakerMod Maker Arm hardware. Its [published API flow](https://dreamlabs.ai/research/dream-1/) takes observations and returns actions. Feed policy actions to a station controller or simulator, and publish measured or simulated joint state back to the viewers. The team has not yet named an external physics implementation. Keep a single authority for contacts and resulting robot dynamics. Reuse the robot team's simulator if it accepts human collision proxies and exposes a tick callback; the repository now includes a [local MuJoCo contact simulator and Unreal viewer](../Capture/README.md#external-maker-arm-contact-simulation) for development. Start with bounded hand/palm and forearm capsules, both actors identified, and an obstacle or articulated simulated arm. Move kinematic/mocap proxies before each physics step; limit speed and displacement or substep fast motion to prevent tunneling/impulses. UE renders results. A real encoder stream can drive a reference twin; simulated impacts must not be converted into physical arm commands. [LiveKit Portal](https://docs.livekit.io/robotics/integrations/portal/concepts/) provides a transport/observer interface; its selection of an active operator is not a physics or contact solver.

## Register the headset, arm model and three cameras

1. **Identify the station first.** [MakerMods](https://www.makermods.ai/maker-arm-station) describes two arms, wrist cameras and an overview. Its [Maker Arm v1 model](https://github.com/makermods-robotics/maker-arm-sdk/tree/0245316c05cb3e8d900f35e70c08e2e18e36731e/urdf/maker_arm) has six rotary joints and two sliding jaws; the supplier marks collision meshes and dynamics unvalidated. The previous I2RT YAM preview was replaced with official Maker Arm geometry in the shared scene. Meanwhile the [LiveKit MakerMods example](https://github.com/livekit-examples/portal-makermods/tree/5f916121c02aa782ac376be1aa1380ecc32e274c) targets **Metal** arms. Verify the actual hardware revision, bases, link lengths, zeroes, gripper travel, telemetry units and driver before using either as a dimensionally accurate twin. Matching joint count is insufficient.
2. **Establish the table frame.** Print the [US Letter ChArUco board](../output/pdf/table-registration-letter.pdf) at 100%, measure the 100 mm scale bar, mount it rigidly outside the reach area and survey its transform to both arm bases. Board definition: 7 × 5 squares at 25 mm, 18 mm markers, OpenCV `DICT_4X4_50`, default IDs/order. The rendered PDF decoded all 17 markers and 24 internal corners. Use a movable calibration copy for multiple lens-calibration views, then the fixed board for registration. Define table axes and units explicitly; convert the full basis (including quaternion handedness) to UE centimetres once. [OpenCV ChArUco calibration](https://docs.opencv.org/4.12.0/da/d13/tutorial_aruco_calibration.html).
3. **Mirror the three robot views.** Use the names [in the Portal example](https://github.com/livekit-examples/portal-makermods/blob/5f916121c02aa782ac376be1aa1380ecc32e274c/portal.yaml): `overhead_camera`, `left_wrist_camera`, `right_wrist_camera`; left/right are the robot's. Calibrate each lens at operating resolution (fx, fy, cx, cy and distortion); fix the overview camera in table coordinates. For each wrist collect several diverse measured arm poses viewing the fixed board; solve link-to-optical-frame hand–eye extrinsics and verify on held-out poses. Parent two UE SceneCapture2Ds to the correct wrist links and one to the table frame. Match intrinsics including principal point/aspect, distortion or undistort both, and evaluate joint telemetry at exposure time. Compare projected board corners in all three real/virtual pairs. Use the camera-poses-plus-timestamps as dataset metadata. A single global FOV or three guessed CameraActors do not reproduce the real views.
4. **Render the AR overlay on the headset.** Use compositor passthrough as the background; render only the simulated robot with a high-contrast outline/ghost material. Stream time-stamped joint values and the registration transform to the headset; do not round-trip headset video through the Mac. For automatic alignment use [Meta's Unreal MRUK passthrough camera access](https://developers.meta.com/vr/documentation/unreal/unreal-mr-utility-kit-features/) with camera permission, intrinsics, frame timestamp and headset/camera pose at exposure time. Solve the fixed board pose, obtaining `T_tracking_table = T_tracking_camera × T_camera_board × T_board_table`; place arms using their surveyed table transforms. Stabilize the transform in tracking space; revalidate after recenter, drift, or table movement. Fast fallback: register three well-separated non-collinear tabletop points using a tracked tip, fit a rigid transform and check a fourth point off the calibration triangle.
5. **Separate registration from robot motion.** Validate with the real arm still at several encoder poses and from several head positions; verify both bases and tool tips. In mirror mode the ghost follows measured robot joints. In contact mode it follows simulated joints: if a person's virtual forearm deflects it, the ghost should depart from the physical arm. Use a label or recording cue to make that intentional divergence legible.

## Rehearsal gates (proposed, not measurements)

| Order | Test and decision |
| --- | --- |
| 1. Transport | Replay a known skeleton and finger curl through the Mac Hub into the existing editor, then direct. Verify subject identity, hierarchy, animation and source time at both consumers. Only keep Hub if the added delay fits the budget. |
| 2. Two humans | Show A's head/torso and independent left/right fingers, and B's upper body, **at the same time**. Have them cross or occlude a hand. No identity swap, phantom contact or recovery sweep. Verify B's root on independent measured targets. |
| 3. Contact | First move a simulated object with each person's hand/forearm separately, then simultaneously contact a robot link. Log actor, joint/collider, input sequence, physics tick and result. Compare normal operation with a delayed/lossy input and disconnect/reconnect. No physical actuation. |
| 4. Timing | Initial demo goals: p95 capture-to-displayed-response under 100 ms and UE presentation of the contact/robot state within one 30 Hz display frame (33 ms) of the scheduled sim result. Measure at least 60 s per route with both streams. Log clock uncertainty, inference, queue, sim apply and render times, drops and p50/p95; use a high-speed side video and visible contact indicator to measure actual motion-to-photon. Vary delay on the simulated remote leg; never infer one-way latency from WAN ping alone. |
| 5. Registration | Initial targets: held-out static tool-tip disagreement ≤ 20 mm at multiple arm/head poses and mean held-out camera reprojection error ≤ 3 px at the tested resolution. Re-approach after walking away/recentering; compare moving tool-tip lag separately. If it misses, show the desktop contact demo and mark AR experimental. |

For the hackathon, prioritize two uniquely identified humans affecting **one simulated object**, and one replay proving the event at the same tick in both systems. Expand to robot links, the three matched camera feeds, then the Quest overlay. Measure without deliberate delay first; emulate a remote participant after the local baseline passes.
