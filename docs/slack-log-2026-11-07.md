## Isaac Sim and the Unreal link (thread with Brian, 1:45 PM to 4:55 PM)

**Set-up facts (Brian, 1:45 PM):** Isaac runs on Luna2, which is remote, and Unreal runs on a laptop on site. The Maker Arm URDF is the one already in this repo. The arm station and Dream-1 work moved to **Saleh and FADI**.

**What Oracle did on Luna2 (reported, not re-verified here):**

- Installed Isaac Sim 6.2 as a separate Python 3.12 environment on Luna2 and converted the Maker Arm URDF to USD (all 9 joints read correctly). Isaac 6.2 uses its bundled converter in place of the old URDF import command.
- At Brian's request (2:25 PM), built the Isaac scene 1:1 from Unreal's own USD export of the saved TheHumanTouch level (63 actors). At load all 18 arm links matched Unreal exactly; after 4 seconds of gravity the worst link drifted 2.7 mm / 0.35° on the folded left arm. A refresh script on Luna2 re-exports and rechecks in about 3 minutes, working from a copy so the live session isn't touched.
- Open: those Isaac build and check scripts live only on Luna2. Oracle offered to commit them to an `Isaac/` folder (without generated USD files) and asked Brian whether to push; no answer is recorded. Isaac follows a snapshot, not live motion, until the bridge is built.

**Decisions Brian confirmed at 4:54 PM**, on how Isaac and Unreal work together while the demo runs:

1. Isaac does the physics and streams results into Unreal, which only draws them. Call it a "physics-based rehearsal" and make no accuracy claims, since motor gains, friction and prop sizes are estimates.
2. The sim arm copies the real arm's 30 Hz stream. **If a virtual object or the person's hands in Isaac would block the arm, both the sim arm and the real arm stop.** Oracle's plan for this: Isaac sends a "hold" message over LiveKit, the robot PC pauses the policy and holds position (no power-off, since the arms have no brakes), triggered on a padded zone a few cm out to cover the SF↔Luna2 lag. It is a software interlock, not a safety stop; the operator stays on the e-stop, and Saleh and FADI need to wire it into the station controller and dry-run it.
3. Draw the human from the same Isaac frame as the props so they stay in sync, and measure the round trip before committing. Brian asked whether Live Link Hub or Stage Monitor can align the feeds; Oracle's answer: Live Link Hub can by timecode (with NTP-synced clocks and the Hub as timecode source), Stage Monitor only watches for drift.
4. Each frame, Isaac sends both arms' joint angles, loose prop poses and a sim timestamp over LiveKit in the portal-makermods message format, so Unreal reads one format from the real arm or the sim. ROS 2 stays on the Isaac machine.
5. Unreal physics is off for everything Isaac owns.
6. Brian asked whether Live Link rebroadcast can reach every machine in the Multi-User session. Oracle's recommendation: LiveKit carries the stream between sites, one Live Link Hub per site subscribes and feeds that site's editors, and Multi-User handles level edits only, not motion.
7. Freeze the table layout before rehearsals (a layout change means a 3-minute re-export).
8. If the stream drops, Unreal holds the last pose and shows a "sim offline" tag.

Oracle's stated next steps were to measure the SF↔Luna2 round trip and build the Isaac → LiveKit publisher with the hold message. None of this is tested on UE 5.8 yet.

## Live Link Hub to Isaac research (12:30 PM)

Following Brian's morning question, Oracle concluded that a Live Link Hub plugin is a credible path (a small skeleton exporter, a timing and transport process, and an Isaac adapter), and that streaming is not the same as synchronization. It found close precedents but no ready-made Hub → Isaac exporter, the nearest being [UE-DTForHRC](https://github.com/TheEngineRoom-UniGe/UE-DTForHRC) and Stereolabs' [ZED Live Link](https://github.com/stereolabs/zed-livelink) and [ZED ROS 2 wrapper](https://github.com/stereolabs/zed-ros2-wrapper). The exporter, gateway and Isaac receiver now in `Capture/isaac/` are the team's own implementation of this path.
